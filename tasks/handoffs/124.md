## Delivery decisions

- Reproduced before the fix: with a done queue row and a registered canonical worktree the task was absent from the snapshot (the new closing tests error without the change).
- Done rows never go through `effective_state` or branch facts: the branch row is still open while the primary row is done, which would read as a mismatch. The closing `Task` is built directly with `lifecycle="closing"`, `readiness="CLOSING"`, and the real queue status.
- Candidate gate: a done row with the profile's closing status (`[x]` or `ACCEPTED`) is considered only when a registered worktree matches its ID, then its canonical branch must be registered. No subprocess runs for other done rows, so refresh cost does not grow with history. `closure_status` runs only for candidates.
- Visible for steps C6, C7, C9, C10 (with a resume action); hidden at C10 with no resume (cleaned up). Other steps (for example C4 `WRONG_WORKTREE`) show `CLOSING` with unavailable progress and no stop or resume, so the console never offers `prepare` for a finished task. A raised lifecycle read keeps the task listed as unavailable.
- Archived rows are checked too, because `integrate stage` archives a closed phase on the candidate tree.
- Visibility keys on the registered worktree, not on a lone leftover branch ref (no cheap branch listing; cleanup removes the worktree first and the branch right after).
- Counts: a closing task counts in `Open` and the `Closing` tab and is excluded from `Done`.
- New `Closing` tab is appended last (existing tab order test kept).
- Dependents keep the existing rule (satisfied by the primary row status).
- Governed: task branches do not edit the queue, so a reserved worktree with a `QUEUED` row derives `IN_PROGRESS`, or `READY_FOR_REVIEW` when the record says so (Review `REQUIRED` or unset, otherwise a mismatch as before). A Governed `READY_FOR_REVIEW` task with a worktree shows cycle time and a console-side `review pending` phase (C3 gate); `closure_status` is not read for it, so a closure stop cannot hide `Review <id>`. Framework identity (task 118) is shown in the `--once` header for the Governed profile (asserted in the new `--once` test).
- Probe on this repository: worktrees for 067, 094, 099, 105 report C10 with a cleanup resume; the real console now lists the rows that are still in the active queue (105) as `CLOSING` with that resume.
