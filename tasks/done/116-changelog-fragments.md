# Task 116 — Replace edits to `[Unreleased]` with per-task changelog fragments

> **ID**: `116`
> **Category**: Release tooling
> **Priority**: 🟡 P2
> **Estimate**: ~2h (split the renderer from the repository check if it grows)
> **Assigned to**: unassigned
> **Session**: Parallel-integration review after Tasks 101 and 111

## Objective

Every task records its user-visible change by editing the same place in
`CHANGELOG.md`, the `## [Unreleased]` section. Like `tasks/QUEUE.md` and
`PROJECT_PLAN.md`, it is a shared file that every parallel task modifies, so two
tasks that integrate close together conflict on it, and Tasks 112 to 115 each add
an entry. Give each task its own changelog fragment file instead, and have the
release command assemble the section at release time. A fragment is a new file
with a unique name, so parallel tasks never touch the same lines.

## Acceptance Criteria

- [ ] A new directory `changelog.d/` holds one Markdown fragment per task, named
  `<TASK-ID>.md` (for example `changelog.d/116.md`), plus a `changelog.d/README.md`
  that states the format and is never treated as a fragment.
- [ ] A fragment contains only subsections whose headings come from this fixed
  list: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`,
  `Documentation`, `Upgrade notes`. Each subsection has at least one bullet.
  Bullets may continue over indented lines. No other heading level and no text
  outside a subsection is allowed.
- [ ] `python3 scripts/check_repository.py` validates every fragment: the file
  name pattern, the allowed headings, non-empty subsections, no `## ` heading,
  and no duplicate heading within one fragment. A malformed fragment fails the
  check with the file and the reason.
- [ ] A shared function renders the fragments into release-section text: headings
  appear in the fixed order above, bullets of the same heading from different
  fragments are concatenated in file-name order, and the output is identical for
  the same inputs on every run.
- [ ] `release.py prepare` builds the new `## [<version>]` section body from the
  rendered fragments, removes the consumed fragment files in the release commit
  (keeping `changelog.d/README.md`), and fails with a specific message when there
  are no fragments and no legacy `[Unreleased]` body. A failed validation restores
  the fragment files together with the other release files.
- [ ] During the transition, a non-empty legacy `## [Unreleased]` body is still
  accepted: it is rendered first and the fragments after it, so tasks already in
  flight that edit `[Unreleased]` keep working. The command reports when it used
  both sources.
- [ ] Template-changing releases are unchanged in meaning: a fragment with an
  `Upgrade notes` heading renders to the `### Upgrade notes` subsection that the
  release check requires, and the kind line is still generated by `prepare`.
  `prepare_release.py` and the release workflow are not changed.
- [ ] `release.py changelog render --version <X.Y.Z>` prints the rendered section
  body without writing, and `--write` applies it to `CHANGELOG.md` and removes the
  consumed fragments, for a migration task that writes its own template-changing
  section. It makes no Git commit.
- [ ] A merge test in a temporary repository shows the point of the change: two
  branches that each add a different fragment merge without conflict, whereas two
  branches that each add a line to `[Unreleased]` in the same place conflict.
- [ ] The criteria of queued, not-started task files that name `[Unreleased]` in a
  `CHANGELOG.md` criterion are changed to name the fragment file instead, with no
  other edit to those files. A task that is in progress, integrated, or archived is
  never edited. The list of changed files is recorded in the handoff.
- [ ] `CONTRIBUTING.md` documents the fragment workflow, the format, that a task
  adds exactly one fragment when it has a user-visible change, and that a change
  with none adds no fragment.
- [ ] Unit tests cover: rendering order and determinism, every malformed-fragment
  case, `prepare` with fragments only, with legacy only, with both, and with
  neither, rollback after a failing validation, the `changelog render` command in
  both modes, and the merge test.
- [ ] `CHANGELOG.md` records the change under `[Unreleased]` for this last time, or
  in a fragment if the implementation is complete enough to use its own format.
- [ ] `python3 scripts/check_repository.py` and the unit tests pass.

## Technical Context

- **Current process**: each task edits `## [Unreleased]`; `release.py prepare`
  moves that body into the new release section and leaves an empty heading.
  Tasks 111 and 098 both added entries there, and Tasks 112 to 115 each have a
  criterion that does the same.
- **Why fragments**: parallel work on shared mutable files is the conflict class
  that Task 100 found for the queue and plan; the same tools solve it for
  changelogs elsewhere (one new file per change, assembled at release, as in
  towncrier and changesets). The queue and plan are handled by Tasks 103 and 104.
- The release kind line, the `baselineChanged` agreement, and the required
  `Upgrade notes` for a template-changing release stay enforced by
  `prepare_release.py` on the assembled section.
- Lean Delivery applies: maintainer tooling only, no change to adopter templates,
  migrations, or the adopter-facing `meridian` CLI.

## Validation

- `python3 scripts/check_repository.py`
- `python3 -m unittest discover -s tests`
- `python3 -m unittest discover -s tests -p 'test_release.py' -v`
- Evidence tier: rendering, validation, rollback, and the merge behavior are
  program-computed and asserted in temporary repositories; no manual evidence is
  required.

## Out of scope

Converting existing `[Unreleased]` or past release sections into fragments,
generating the queue and plan (Tasks 103 and 104), changing the release workflow
or `prepare_release.py`, template changes for adopters, and publishing a release.
